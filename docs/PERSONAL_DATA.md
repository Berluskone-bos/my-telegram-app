# Персональные данные (152-ФЗ): что хранится, куда идёт, план переноса в РФ

Статус на 18.11.2026. **Я не юрист; это техническая сводка и план, а не юридическое заключение.** Перед переносом и подачей уведомлений нужна консультация юриста по персональным данным (ПДн).

## 1. Какие ПДн российских клиентов хранятся в базе (проверено: схема базы, тестовая копия)
| Таблица | Поля с ПДн |
|---|---|
| `orders` | `user_id` (Telegram ID), `user_name`, `phone`, `address`, `street`, `house`, `entrance`, `apartment`, `comment`, реферальные поля |
| `customer_profiles` | `user_id`, `name`, `phone`, `street`, `house`, `entrance`, `apartment` |
| `route_stops` | `client_name`, `phone`, адрес, **координаты** `lat/lon`, `client_chat_id`, `comment` |
| `user_garage` / `vin_lookup` | `user_id`, **VIN**, название автомобиля (VIN — косвенно идентифицирует человека) |
| `bonus_ledger` | `user_id`, история бонусов |
| `widget_messages` | `chat_id` |
| `notification_outbox` | `payload` — текст уведомлений целиком (имя, телефон, адрес клиента); отправленные удаляются через 14 дней, недоставленные — через 90 (код `outbox.js`) |
| `couriers` | ФИО, телефон, госномер (данные работников/подрядчиков) |
| `admin_sessions`, `admin_audit` | IP-адреса администраторов |
Номеров банковских карт в базе нет (проверено по схеме: есть только способ и статус оплаты).

## 2. Где происходит первичная запись и куда данные уходят (по коду и живому Railway)
1. Клиент открывает Mini App (статические файлы с GitHub Pages — серверы GitHub, США/CDN). Сами файлы ПДн не содержат.
2. Форма заказа отправляется запросом `POST /api/order` на сервер **`gulf-bot` в Railway, регион sfo (Сан-Франциско, США)**. **Это первая точка приёма данных.**
3. Сервер сохраняет заказ в PostgreSQL на Railway, **регион sfo (США)**. Это основное хранилище.
4. Уведомления о заказе (имя, телефон, адрес) отправляются в **Telegram** (админ-чат, курьеры, клиент) — иностранный сервис.
5. Адрес отправляется в геокодер Яндекса (российский сервис) для координат — внутри РФ, если запрос идёт к российским серверам (не проверялось отдельно).
6. Подбор по VIN: запросы уходят во внешний сервис каталога (PartsAPI); какие данные и в какую страну — **не проверено** (проверить: передаётся ли VIN вместе с чем-то, идентифицирующим клиента).
7. Резервные копии (если настроить по `docs/BACKUP.md`) — хранить в РФ.

## 3. Что говорит закон (по найденным источникам; сверить с юристом)
- Требование локализации (ч. 5 ст. 18 152-ФЗ): при сборе ПДн граждан РФ запись, систематизация, накопление, хранение, уточнение и извлечение должны выполняться с использованием баз данных **на территории РФ**. Исключения узкие. *Эта формулировка известна мне из общих знаний; в найденных страницах (Контур, vitvet, h-cons) её текст не приведён, поэтому как «проверенную по первоисточнику» её не считаю.*
- Трансграничная передача (ст. 12), с 01.03.2023: оператор **до начала передачи** уведомляет Роскомнадзор (подтверждено статьёй Контур); до 10 рабочих дней нельзя передавать в страны без адекватной защиты. США в список стран с адекватной защитой, насколько я знаю, не входят (не проверено).
- Локализация и трансграничная передача — **разные** требования: уведомление о передаче за рубеж не отменяет обязанность хранить первичную базу в РФ.
- Штрафы: нарушение локализации — ч. 8 ст. 13.11 КоАП. По найденной публикации (kod.ru, 10.11.2026): должностные лица — до 200 тыс. руб., юрлица — до 6 млн руб., при повторном нарушении больше; реальный пример — штраф 100 тыс. руб. чиновнику за иностранную платформу на сайте. Суммы для **ИП** в источниках не найдены; два других источника расходятся в деталях. **Суммы не сверены с текстом КоАП.** За утечки действуют отдельные, более крупные штрафы (ч. 7: от 1 до 3 млн руб. первичное и от 3 до 15 млн руб. повторное для организаций — по vitvet, с оговоркой страницы о внутренних противоречиях).
- Роскомнадзор проверяет и по обращениям граждан; иностранные площадки в публикациях 2026 года фигурируют как основание штрафов.

## 4. Вывод
Сейчас и первичный приём (сервер), и хранение (база) — в США. **Если вы собираете ПДн граждан РФ (имя, телефон, адрес — собираете), текущая схема, вероятнее всего, не соответствует требованию локализации.** Окончательная квалификация (в том числе по Telegram как каналу связи) — вопрос к юристу. Технически безопасный путь — перенести и сервер, и базу в РФ. Одной базы недостаточно: пока запросы принимает сервер в США, «первичная запись» происходит там.

## 5. План переноса в РФ (написано; не выполнялось; на живом сервисе ничего не менялось)
**Шаг 0. Решения владельца и юриста (1–2 недели, без кода)**
- Консультация юриста: статус ИП как оператора, уведомление об обработке ПДн в Роскомнадзоре, уведомление о трансграничной передаче (если Telegram/иное считается передачей), политика `privacy.html`, согласие на ПДн.
- Выбор провайдера в РФ. Кандидаты: Yandex Cloud (Managed PostgreSQL + виртуальная машина/контейнеры), Selectel, Timeweb Cloud, VK Cloud. Критерии: дата-центр в РФ, управляемый PostgreSQL с автокопиями, цена, оплата с ИП. Актуальные цены и условия я не проверял — запросить у провайдеров.
**Шаг 1. Подготовка кода (я, 1–2 PR)**
- `Dockerfile` для `bot/` и `.env.example` (в TASKS это п. 12, не сделано); запуск без Railway-специфики (порт, `WEBHOOK_URL`, `DATABASE_URL`).
- Проверить, что в окружении РФ доступен Telegram Bot API (webhook принимается по HTTPS с валидным сертификатом; исходящие запросы к `api.telegram.org` проходят). Это нужно проверить **до** переноса на тестовой службе.
- Проверить сервисы за рубежом: PartsAPI, шрифты Google в админке.
**Шаг 2. Тестовый стенд (неделя)**
- Поднять копию в РФ с тестовыми данными (из `backup/` — копия восстанавливается скриптом `restore.sh`), прогнать `npm test`-сценарии заказа и уведомлений, замерить задержку.
**Шаг 3. Перенос (окно 30–60 минут ночью, предупредить клиентов)**
1. Остановить `gulf-bot` в Railway (приём заказов выключен; клиенты увидят временную недоступность).
2. Сделать финальную копию `backup.sh`, восстановить в РФ-базу `restore.sh`, сверить число строк по таблицам.
3. Запустить сервер в РФ с новой `DATABASE_URL`; установить webhook трёх ботов на новый адрес; обновить `API_BASE`/адрес сервера во фронтенде (GitHub Pages) и `WEB_APP_URL` в BotFather, если домен меняется.
4. Тестовый заказ, уведомление в админ-чат, блок «Состояние системы».
**Шаг 4. После переноса**
- Неделю держать старую базу в Railway выключенной (для отката), затем удалить и **зафиксировать акт уничтожения** данных в США (по требованиям Роскомнадзора, акт хранится 3 года — Контур).
- Обновить `privacy.html`, `docs/ARCHITECTURE.md`, `docs/MEMORY.md`.
- Фронтенд на GitHub Pages ПДн не хранит; при желании перенести и его (не обязательно).
**Риски:** простой при переносе; ошибки в вебхуках; бот может быть недоступен из РФ-хостинга без прокси (проверить в шаге 1); цена. **Откат:** вернуть webhook и `DATABASE_URL` на Railway (старая база цела до шага 4).
