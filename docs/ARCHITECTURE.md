## Заказ (как работает сейчас)
1. Клиент оформляет заказ в Mini App → `POST /api/order` с `X-Telegram-Init-Data`.
2. Сервер проверяет подпись initData (HMAC по токену бота), лимит запросов, `Idempotency-Key` (повтор вернёт тот же заказ), **берёт цены из БД**, считает доставку по `delivery_zones` (СПб: 300 ₽, бесплатно от 5 000 ₽; ЛО — вручную).
3. Заказ пишется в БД в транзакции; остаток товара списывается (`UPDATE … WHERE stock >= qty`, иначе 409 «нет в наличии»); при отмене остаток возвращается; уведомление уходит в админ-бот. Статусы меняются из `admin.html` и курьерского бота.
4. Оплаты в системе нет (оплата курьеру/наличными, как в коде) — эквайринг в планах.

## Витрина и заглушки
`data/catalog.json` — запасная витрина: 13 товаров первой партии (артикулы ООО «Сан Трип») + 5 «заглушек» (`coming_soon: true`: показываются без цены и кнопки). Основной источник — **база данных** (`products`) через `GET /api/catalog` (цены, остатки, `in_stock`, `stock_left` при ≤5); `catalog.json` — запасной вариант. Товары добавляются и правятся в админке (вкладка «Товары»). Учёт остатков включается при появлении первого положительного остатка и сохраняет состояние в `app_flags.stock_tracking_enabled`; после исчерпания последнего остатка режим не отключается.

## Интерактивные карточки Telegram (виджеты, с 15.11.2026)
Bot API 10.4: `sendWidget` (HTML + `chat_data`), `editMessageWidgetData` (меняет только данные, без уведомления), нажатия — обновление `widget_query` (главный вебхук `/webhook/main`, ответ `answerWidgetQuery`). Карточки: **трекер заказа** (клиентский бот, `kind=tracker`, ref = номер заказа), **маршрутный лист** (курьерский бот, `kind=route`, ref = id маршрута), **сводка дня** (админ-бот, `kind=summary`, ref = chat_id админа). Состояние — таблица `widget_messages` (`active=false` — карточка выключена, работают обычные сообщения). Отправка и правка идут через очередь `notification_outbox` (методы `sendWidget`/`editMessageWidgetData`, `edit_ref = «kind:ref»`, запасной вариант в `on_sent.fallback`). Лимиты Telegram: HTML ≤ 32 КБ и ≤ 4096 Б в сжатом виде, данные ≤ 1024 Б (проверяет `widgets.checkWidget`). Выключатель: `WIDGETS_ENABLED=0`. **Статус на 16.11.2026: Telegram отвечает обычным ботам `INPUT_MEDIA_WIDGET_NOT_ALLOWED`, карточки не показываются;** бот ставит автопаузу на 6 часов (`widgets.pauseWidgets`) и работает обычными сообщениями, затем пробует снова. В карточках только то, что разрешено в виджетах: цвета темы `--tg-theme-*`, системные шрифты, без `color-mix`, `vh`, полей ввода, сети, внешних картинок.

## Подбор жидкостей (работает; с 11.11.2026 — каталог ТО PartsAPI)
Файлы в `bot/`: `oil-catalog.js` (запросы и разбор), `oil-systems.js` (разбор по системам и подбор товаров), `oil-routes.js` (маршруты), `partsapi-cache.js` (кэш и лимит); фронтенд — `js/oil.js`, `css/oil.css`. Таблицы базы: `api_cache`, `api_request_log`, `to_vehicles` (название модификации по `typeId`), `product_approvals`; старые таблицы `vehicles`, `vehicle_*` не используются.
```
toMakes (id марки) → toModels (brandId) → toTypes (modelId) → typeId
                                                              ▼
                                  toDopusk (typeId): specifications[] (объём, вязкость, допуски по системам) + oils[]
                                                              ▼
   oil-systems.js: системы (двигатель, коробка [автомат/вариатор/робот/механика], редукторы, ГУР, антифриз, тормозная, кондиционер)
   + товары магазина: «по допуску» → «по вязкости» → «по типу»
```
Если PartsAPI не знает машину — страница показывает «в базе нет объёмов и допусков» и товары магазина по системам без утверждения совместимости. VIN: `VINdecode` определяет марку и модель, дальше выбор модификации из каталога (российские VIN Z94… PartsAPI не знает — предлагается ручной выбор, марка подставляется по WMI).

Эндпоинты: `GET /api/oil/by-vin`, `/makes`, `/models`, `/cars`, `/by-car` (`car_id` = `typeId`), `/usage` (админ); `GET/PUT /api/products/:id/approvals` (админ). 30 запросов в минуту; безопасные сообщения (`userError`). Кэш: справочники 90 дней, `toDopusk` 180 дней, пустой ответ — 1 час; суточный лимит `PARTSAPI_DAILY_LIMIT` (45) на метод; при обрыве соединения 3 попытки. Ключи — только переменные Railway `PARTSAPI_KEY_*` (`VINDECODE`, `TOMAKES`, `TOMODELS`, `TOTYPES`, `TODOPUSK`).

| Метод | Назначение | Статус |
|---|---|---|
| `VINdecode` | VIN → авто; ID модификации в `typeNumber`/`carId` | используем |
| `getMakes` / `getModels` / `getCars` | марки (~735, двойники «AUDI (FAW)») → модели → модификации (`CAR_ID`) | используем |

| `getCarsByOilSpecification` | обратный поиск | не проверен |

⚠ **Не подтверждено:** совпадают ли `CAR_ID` и `typeNumber` с `carId`/`typeId` у `GetFillVolumes`/`toDopusk` (проверять `tools-partsapi/` на реальных ключах — задача A6).

## Известные ограничения
- Лимиты запросов и дедупликация заказов — в памяти процесса (при нескольких копиях сервера не общие).
- Корзина и избранное пока в `localStorage` (задача C6). Скидка по обороту и реферальные бонусы считаются на сервере (`loyalty_tiers`, `discount.js`, `referral.js`, обновления 21 и 23; UI профиля — C4c). Профиль и гараж частично на сервере (`customer_profiles`, `user_garage`).
- VINdecode опирается на TecDoc и может не знать VIN российской сборки (Z94, XTA и др.).
- Интерактивные карточки: на живом сервисе Telegram их пока не принимает (`INPUT_MEDIA_WIDGET_NOT_ALLOWED`, см. TASKS.md, обновление 28), поэтому вид карточек, `widget_query` и серые кнопки не проверены.
- Живая работа ботов в Telegram из среды Claude не проверялась (состав служб Railway и подключение бота к базе проверены 17.11.2026 по логам); серверные проверки выполнялись на локальной копии с подставными ответами Telegram.

## Админ-панель: индивидуальная авторизация и роли (актуально на 19.11.2026)

Админ-панель расположена в `admin.html` (GitHub Pages); защищённые API обслуживает Railway/Express. Общий `ADMIN_API_KEY` удалён владельцем из production Railway Variables; вход по этому ключу больше не является рабочей схемой. Сотрудники входят по индивидуальным логину и паролю. Пароли хранятся в виде хешей scrypt; сервер выдаёт сессию, а защищённые маршруты проверяют сессию и разрешение на сервере.

Роли и границы доступа:
| Роль | Доступ |
|---|---|
| Администратор | Полный доступ, включая управление сотрудниками и настройками |
| Менеджер | Обзор, заказы и обработка, клиенты, продажи/аналитика |
| Оператор | Обзор, просмотр и обработка заказов |
| Кладовщик | Обзор, заказы в пределах складских задач, товары и остатки; без клиентских персональных данных |

Права проверяются серверным middleware на API; скрытие вкладок в интерфейсе не считается защитой. Для заказов действует серверная allowlist-фильтрация: администратор и менеджер видят полную запись; оператор в списке получает ID/номер, телефон, сумму, статус, тип доставки и дату, а в деталях — дополнительно адрес и состав заказа. Оператор не получает имя клиента, Telegram user_id, статус оплаты и прочие платёжные/служебные поля; способ оплаты и примечание/инструкция к заказу сохранены как рабочие данные. Кладовщик получает только складские поля без клиентских ПДн. Неизвестная роль обрабатывается fail-closed. Регрессионные тесты фиксируют точные наборы разрешённых полей. Для `GET /api/admin/dashboard` имена последних заказчиков также исключаются для ролей без `customers.view` (PR #57).

PR #54 добавил индивидуальные учётные записи, роли, серверные разрешения и управление сотрудниками/сессиями; PR #55 перевёл `/api/webhook-info` на сессию и `settings.manage`; PR #56 добавил ролевую фильтрацию персональных данных заказов; PR #57 исправил выдачу имени клиента в обзорной панели. См. `MEMORY.md` и `TASKS.md`.

Ограничения и оставшиеся меры безопасности после аудита:
- Защита от перебора паролей пока основана на локальном в памяти процесса счётчике; она не общая для нескольких экземпляров и сбрасывается после рестарта. Нужен централизованный rate limit и ограничение на учётную запись.
- Проверить `Cache-Control: no-store` на всех защищённых GET API, возвращающих персональные/служебные данные.
- Удалить оставшийся неиспользуемый legacy-код авторизации через `ADMIN_API_KEY` из репозитория после отдельной проверки всех ссылок.
- CSP содержит `'unsafe-inline'`; рассмотреть nonce/hash и проверить совместимость.
- Провести динамическое тестирование всех API на IDOR/BOLA и матрицу ролей. Статический просмотр не доказывает отсутствие всех обходов.


## Оценка доставки (19.11.2026)
- Оценка доступна клиенту через обычное сообщение и карточку трекера. Обычный callback имеет формат `rate_<courierId>_<routeStopId>_<rating>`; widget_query использует номер заказа. Оба пути вызывают единые транзакционные методы `rateCourierForStop()` / `rateCourierForOrder()`.
- `bot/bot.js` обрабатывает callback клиентского бота через строгий парсер `bot/delivery-rating.js`. Метод `db.rateCourierForStop()` проверяет Telegram ID отправителя по `orders.user_id`, соответствие остановки назначенному курьеру, статус `route_stops.status = 'delivered'` и статус заказа `DELIVERED`/`COMPLETED`.
- `route_stops.client_rating` хранит оценку 1–5; карточка трекера только отображает результат и не является источником защиты от повторов. Поле nullable, поэтому исторические доставки остаются без оценки. PostgreSQL-транзакция блокирует строку остановки и обновляет оценку и агрегат курьера один раз; повторная оценка не меняет рейтинг.
- Идемпотентная миграция выполняется через `bot/db.js:initDB()`. Старый callback без ID остановки отклоняется.

- При старте после создания `widget_messages` выполняется идемпотентный backfill прежних оценок tracker-widget в `route_stops.client_rating`; старые карточки помечаются `canRate=false`. Backfill не меняет агрегаты `couriers.rating/rating_count`, а только фиксирует уже начисленную оценку для защиты от повторов.

## Статус «Не доставлен» и карточка маршрута курьера (обновление 38)
Конечный автомат заказа дополнен `DELIVERY_FAILED`: `SHIPPING → DELIVERY_FAILED → READY_FOR_SHIPMENT | CANCELLED`. Переход в `DELIVERY_FAILED` выполняет только `db.failDeliveryStop` (одна транзакция: заказ → маршрут → остановка), из админки статус недоступен. Курьерский бот показывает маршрут одним сообщением (`bot/courier-card.js`), состояние остановки (`route_stops.stage`) хранится в базе. Админка выводит колонку «Не доставлены» с причиной из `route_stops.fail_reason` (поле `fail_reason` в `GET /api/orders`, доступно всем ролям, у которых есть список заказов).

## Admin API cache policy
Все маршруты, защищённые реальным middleware `verifyAdmin` из `bot/admin-auth.js`, устанавливают `Cache-Control: no-store` после успешной аутентификации. Это общее правило, а не обязанность каждого обработчика. Проверка IDOR/BOLA по полной матрице ролей остаётся отдельной задачей.


## Ограничение попыток входа в админку
Счётчик неудачных попыток хранится в PostgreSQL в `admin_login_attempts`; ключ — HMAC-SHA-256 от IP-адреса, исходный IP в этой таблице не сохраняется; HMAC-ключ берётся из `WEBHOOK_SECRET` (fallback — секретный ключ админки). Это обеспечивает единый лимит между несколькими процессами и сохранение блокировки после перезапуска. Записи старше суток удаляются периодической очисткой. Параметры лимита задаются в `createAdminAuth` (`maxFails`, `blockMs`).

## Ролевой доступ к данным диспетчеризации
- `admin` (`*`) получает полные данные курьеров и маршрутов через `/api/couriers` и `/api/routes` для экрана доставки.
- `operator` (`routes.manage`) получает только `couriers: id, name, is_active` и `routes: id, courier_id, stops[].order_id`, необходимые экрану заказов для назначения и отображения курьера. Телефоны и Telegram-идентификаторы курьеров, а также ПДн клиентов в остановках маршрута в этих ответах не передаются.
- Ответы построения/одиночного назначения маршрута для оператора содержат только метаданные маршрута; полный список остановок остаётся только у admin. Оптимизация маршрута требует `settings.manage`.
- Реализация и регрессионные тесты: `bot/admin-dispatch-visibility.js`, `test/admin-dispatch-visibility.test.js` (PR #93).

## Cache policy for customer profile
Маршруты `GET /api/profile` и `PUT /api/profile` устанавливают `Cache-Control: no-store` после проверки подписанного Telegram initData, поскольку ответы содержат номер телефона клиента. Регрессионная проверка находится в `test/order-api.pg.test.js`.


## Dashboard role response matrix
`GET /api/admin/dashboard` использует права роли для полей ответа: `sales.view` управляет выручкой и числом клиентов, `customers.view` — именами клиентов в последних заказах, `inventory.view` или `products.view` — остатками и низким запасом. Ответы защищены `Cache-Control: no-store`; регрессионные проверки четырёх ролей находятся в `test/admin-dashboard.test.js`.


## Права на каталог и склад
- `GET /api/products`: администратор получает полную карточку; роль warehouse — только `id`, бренд, категория, название, артикул, объём, остаток, минимальный остаток и статусы наличия.
- `POST /api/products` и `PUT /api/products/:id`: требуют `settings.manage` (управление каталогом).
- `PATCH /api/products/:id/stock`: требует `inventory.manage`; разрешены только целочисленные неотрицательные `stock` и/или `min_stock` в пределах 0–1 000 000.
- `GET/PUT /api/products/:id/approvals`: требуют `settings.manage`; кладовщик не получает допуски через отдельный endpoint.


## Постоянное состояние складского учёта
Первый заказ при наличии хотя бы одного активного товара с положительным остатком устанавливает `app_flags.stock_tracking_enabled` в той же транзакции, что и заказ. Режим остаётся включённым, даже когда все остатки становятся нулевыми. Публичный каталог использует сохранённый флаг, поэтому не показывает распроданный товар как доступный. Ручная корректировка поля `stock` через DB adapter также включает режим. Регрессия покрывается `test/orders-stock.pg.test.js` (PR в работе).


## Атомарная активация складского учёта
При ручной корректировке поля `stock` изменение товара и запись `app_flags.stock_tracking_enabled` выполняются в одной транзакции. Флаг устанавливается только если UPDATE действительно изменил существующую строку товара. Это не позволяет случайному или ошибочному ID включить глобальный режим складского учёта. Регрессионный тест находится в `test/orders-stock.pg.test.js` (PR #98).


## Очередь клиентских уведомлений курьера
Обработчики этапов `enroute` и `arrived` ожидают завершения `queue.notify`: callback подтверждается после записи уведомления в `notification_outbox`, а не раньше. Это уменьшает неопределённость при повторных нажатиях и обеспечивает детерминированное поведение интеграционных проверок.


## Жизненный цикл складского остатка
- Списание выполняется в одной транзакции с созданием заказа; UPDATE уменьшает stock только при условии `stock >= qty`. Если хотя бы одна позиция не проходит проверку, транзакция заказа откатывается.
- `stock_deducted` фиксирует, требуется ли возврат товара при отмене. Отмена/удаление активного заказа возвращает остаток один раз; повторная отмена не дублирует возврат.
- При `DELIVERY_FAILED` остаток остаётся списанным/зарезервированным, пока заказ ожидает повторную отправку или решение об отмене. При отмене возвращается один раз.
- После успешной доставки/завершения товар остаётся списанным; автоматического возврата в склад нет.
- Режим учёта хранится в `app_flags.stock_tracking_enabled` и не отключается автоматически при нулевых остатках.


## Одноразовая активация складского учёта в production
По согласованию владельца `ENABLE_STOCK_TRACKING_ON_STARTUP=true` выполняет идемпотентный INSERT `app_flags.stock_tracking_enabled` при инициализации БД. Не меняет таблицы `products` и `orders`. После успешного запуска env-флаг выключается, а запись в `app_flags` остаётся постоянной. Механизм предназначен для однократного восстановления явно согласованного режима на production.


## Единый порядок блокировок маршрута
Для операций, которые одновременно затрагивают заказ, маршрут и остановку, применяется порядок `orders → delivery_routes → route_stops`. `failDeliveryStop` и `setStopStage` уже соблюдали порядок route → stop (для этапа нет блокировки заказа); `completeDeliveryStop` приведён к тому же порядку после блокировки заказа. Это исключает цикл, когда один callback удерживает маршрут и ждёт остановку, а второй удерживает остановку и ждёт маршрут. Регрессия в `test/route-lock-order.pg.test.js`.


## Защита завершённого самовывоза
`PICKED_UP` — терминальный статус: после фактической выдачи товар у клиента. Отмена по номеру заказа из админ-бота не должна обходить `orderTransitionAllowed`; `cancelOrderByNumber` исключает `PICKED_UP` наряду с уже отменёнными и доставленными/завершёнными заказами. Регрессия в `test/cancel-picked-up.pg.test.js`.
