# RULES — что делать и чего избегать

## Работа с владельцем
- Владелец не программист. Отвечать **по-русски**, объяснять пошагово: что скачать, куда нажать, какую команду ввести и что должно появиться на экране («Что вы должны увидеть»).
- Руководства оформлять в `.docx` в том же стиле, что файлы в `1-документы/`: тёмные блоки для команд, зелёные блоки результата, жёлтые «Важно».
- Не писать «готово», пока не проверено. Различать: «написано», «проверено на тестовой базе», «проверено на VPS владельца».
- Если не знаешь название или параметры метода API — не выдумывать, попросить описание (так и делали).

## Стек и зависимости
- Фронтенд: чистый JavaScript, один `index.html`. Без фреймворков и сборщиков, пока владелец сам не решит иное.
- Бэкенд: Node.js + Express в `bot/` (Railway). Библиотеки сейчас: `express`, `pg`, `dotenv`, `node-telegram-bot-api`; добавлять `jsonwebtoken`/`bcrypt` только вместе со входом по SMS. Новую зависимость добавлять только с объяснением, зачем, и записью в `MEMORY.md`.
- База данных: PostgreSQL на Neon. Схема меняется SQL-файлами с `IF NOT EXISTS` (их запускают в Neon SQL Editor); таблицы создаёт и `bot/db.js` при старте.
- Комментарии в коде — по-русски, объясняют «зачем», а не «что».

## Безопасность (обязательно)
- Секреты (ключи PartsAPI, пароль БД, SMS, `JWT_SECRET`) — только в `.env` на сервере. Никогда в HTML, в `index.html`, в репозитории GitHub Pages. Тестовые ключи PartsAPI в учебных скриптах допустимы, боевые — нет.
- Цены, суммы, скидки и бонусы считает сервер. Любые числа от клиента считать недоверенными.
- Все SQL-запросы — только параметризованные (`$1, $2`). Никакой конкатенации строк.
- Любой текст из базы или внешнего API выводить в HTML через `esc()` (экранирование). Не использовать `innerHTML` с сырыми данными.
- Для данных пользователя Telegram на сервере проверять подпись `initData` (hash по bot token). `initDataUnsafe` на клиенте — только для отображения имени.
- Админ-адреса — только с `verifyAdmin` (заголовок `x-admin-key`, значение `ADMIN_API_KEY` из Railway; проверка сервером, не страницей). Любой вывод пользовательского текста в админке и магазине — через `esc()`. Курьерские кнопки: проверять, что маршрут и остановка принадлежат этому курьеру. Webhook-и: `secret_token`. Когда будет вход по SMS: код не чаще 1 раза в 60 секунд, хэш, 5 минут, 5 попыток.
- Репозиторий публичный (решение владельца 07.11.2026: цены не считаются тайной, документы лежат в нём же). Но токены, пароли, ключи API, строки подключения к БД, персональные данные клиентов и заказы в репозиторий класть нельзя никогда. Если секрет всё же попал в Git — сразу отозвать (BotFather `/revoke`, сброс пароля Neon): удаление файла историю не чистит.

## PartsAPI и расход запросов
- Каждый вызов PartsAPI платный/лимитированный. Любой запрос идёт только через `cachedApi()` из `partsapi-cache.js`.
- Не кэшировать ошибки. Пустые ответы кэшировать на 1 час.
- Ключ API в `api_cache` не писать.
- Любые изменения методов фиксировать в `ARCHITECTURE.md` (таблица методов).

## Подбор масла — правила безопасности для клиента
- Допуски товара (`product_approvals`) вносить **только** из этикетки или сертификата производителя. Лишний допуск = риск залить в двигатель неподходящее масло. Это ответственность магазина.
- Если допусков у товара нет — он не получает пометку «подходит по допуску». Но в подборе он может быть показан по вязкости или типу (решение владельца 10.11.2026: спецификации меняются) — только с пометкой «сверьте допуск с руководством». Никогда не писать «подходит» без этой оговорки.
- Подпись `initData`: из строки проверки исключается только `hash`; секрет = HMAC_SHA256(ключ «WebAppData», токен бота). Не менять порядок.
- Ключи PartsAPI — только в переменных Railway (`PARTSAPI_KEY_*`), в код не вписывать даже тестовые.
- Перед сборкой обновления брать свежую `main`: владелец загружает файлы поверх, старые копии перезаписывают новые.
- Показывать объём заправки из `GetFillVolumes`; поле `volume` из `toDopusk` — это фасовка канистры, не заправка.
- Сравнение допусков — без учёта регистра, пробелов и точек («VW 504.00» = «VW 504 00»).

## Бизнес-правила
- Не называть магазин «Gulf Western Oil»: магазин — Автопромойл, Gulf Western Oil — бренд товара.
- Формулировки о статусе («официальный представитель/дистрибьютор») — только в той редакции, что указана в документах Сан Трип/Gulf Western Oil; владелец подтвердил, что документы есть. Закупочные цены (`cost_price`) клиенту и в публичные адреса API не отдавать.
- Светлая тема единственная: не добавлять переключатель и не подстраиваться под тему Telegram.
- Каждая продажа маркированной канистры должна списывать код DataMatrix и пробивать фискальный чек — это условие запуска продаж, не «потом».
- Пока нет согласия на обработку персональных данных (чекбокс) — данные не сохранять.

## Код и ошибки
- Серверные адреса оборачивать в обработчик ошибок (`wrap`): клиенту — понятное сообщение по-русски, без трассировки.
- Заказ записывать в транзакции (`BEGIN/COMMIT/ROLLBACK`).
- Адрес без токена — 401; неверные данные — 400; исчерпан лимит PartsAPI — 503.
- Перед передачей файлов владельцу: `node --check` для `.js`, прогон на тестовой БД, для HTML — открыть в браузере и проверить мобильную ширину.

## Что не делать
- Не переписывать работающие файлы целиком ради «улучшения». Менять точечно и записывать в `MEMORY.md`.
- Не менять названия таблиц и полей без записи в `MEMORY.md` — по ним написан SQL в руководствах.
- Не просить у владельца логины и пароли. Доступ к кабинетам даёт он сам; данные оттуда вставляет текстом.
- Не копировать логотипы, макеты и тексты Gulf Western Oil как свои материалы.
