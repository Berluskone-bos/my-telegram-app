# Резервное копирование PostgreSQL и восстановление после аварии

Статус на 18.11.2026. Обозначения: **написано** — код/инструкция есть в репозитории; **проверено на тестовой копии** — прогнано на локальной тестовой базе; **проверено на живом сервисе** — подтверждено на Railway.

## 1. Что выяснено про Railway (проверено на живом сервисе, 18.11.2026)
- Рабочая база — служба `Postgres` (образ `postgres-ssl:18`, том `postgres-volume` 500 МБ, регион sfo).
- Тариф рабочего пространства — **Hobby**. Лимит копий тома у этого тарифа = **0** (`maxBackupsCount = 0`, ответ Railway-агента). Значит **автоматических резервных копий Railway у вас нет**, и создать их на этом тарифе нельзя.
- PITR (восстановление на момент времени) для этого образа не включён: признаков архивации журнала нет.
- Не проверено: вкладка **Backups** у тома в панели Railway (мои инструменты её не читают). Откройте её и убедитесь, что там пусто (см. шаг 0 ниже).
- Вывод: до настройки собственных копий единственный экземпляр данных живёт на одном томе 500 МБ. Потеря тома = потеря всех заказов, клиентов, бонусов.

## 2. Что сделано: собственные ежедневные копии (написано + проверено на тестовой копии)
Папка `backup/` в репозитории:
- `backup.sh` — `pg_dump` (формат custom, сжатый) → шифрование AES-256 паролем `BACKUP_PASSPHRASE` → самопроверка (копия расшифровывается и читается `pg_restore --list`, размер не меньше 2000 байт) → загрузка в S3-совместимое хранилище → удаление старых копий.
- `restore.sh` — восстановление **только в новую пустую базу** (в непустую или с неверным паролем — отказ).
- `Dockerfile` — клиент PostgreSQL **18** (та же версия, что у базы) + aws-cli + openssl.

### Расписание и срок хранения (предложение, можно изменить переменными)
| Что | Когда | Сколько хранить |
|---|---|---|
| Ежедневная | каждый день 03:00 UTC = 06:00 МСК | 14 штук (`KEEP_DAILY`) |
| Недельная | воскресенье | 8 штук (`KEEP_WEEKLY`) |
| Месячная | 1-е число | 12 штук (`KEEP_MONTHLY`) |

Максимальная потеря данных при аварии (RPO) — до 24 часов. Если потеря суток заказов недопустима — запускать чаще (например, каждые 6 часов: `0 */6 * * *`); хранилище это выдержит (копия весит десятки КБ).

### Что проверено на тестовой копии (локальный PostgreSQL 16, копия делалась тем же скриптом)
- Копия создаётся, шифруется, читается: 26 таблиц с данными.
- Восстановление в новую пустую базу: 26 таблиц, **число строк совпало во всех таблицах**, заказы читаются.
- Неверный пароль → восстановление отказывает, база остаётся пустой.
- Повторное восстановление в непустую базу → отказ.
- Ротация: при `KEEP_DAILY=3` лишние старые копии удалены, новые остались.

### Что НЕ проверено
- **Не проверено на живом сервисе:** сборка `Dockerfile`, запуск как Cron-служба Railway, загрузка в реальное хранилище, restore копии из хранилища. Локально использовался PostgreSQL 16, у Railway — 18; клиент 18 в `Dockerfile` рассчитан на это, но пока не прогонялся.
- Работа с настоящим S3 (ветка `aws s3`) проверена только по синтаксису; в тесте использовалась папка.

## 3. Что должен сделать владелец (один раз, ~30 минут; секреты — только в Railway, мне их не присылать)
0. Railway → проект → служба `Postgres` → том → вкладка **Backups**. Запишите, что там (скорее всего «недоступно на вашем тарифе»).
1. Создайте корзину в S3-совместимом хранилище. Рекомендую российское (Яндекс Object Storage или Selectel): копии содержат персональные данные клиентов, их тоже нужно хранить в РФ (см. `docs/PERSONAL_DATA.md`). Создайте отдельного пользователя с правами **только на эту корзину** и ключ доступа.
2. Придумайте длинный пароль шифрования (20+ символов) и **сохраните его в менеджере паролей/сейфе отдельно от Railway**. Без него копии не расшифровать — ни вам, ни мне.
3. Railway → проект `Gulf_Western_Oil_bot` → New → GitHub Repo → тот же репозиторий → в настройках службы: **Root Directory = `/backup`**, builder = Dockerfile, **Cron Schedule = `0 3 * * *`**. Назовите службу `db-backup`.
4. Переменные службы `db-backup`: `DATABASE_URL` = ссылка на переменную службы Postgres (`${{Postgres.DATABASE_URL}}`), `BACKUP_PASSPHRASE`, `BACKUP_S3_BUCKET`, `BACKUP_S3_ENDPOINT` (для Яндекса `https://storage.yandexcloud.net`), `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `AWS_DEFAULT_REGION` (для Яндекса `ru-central1`).
5. Нажмите Deploy / Run now.

**Что вы должны увидеть:** в логах службы `db-backup` строки `[backup] копия gulf-….dump.enc: … байт, таблиц с данными: 26` и `[backup] готово`; в корзине — папка `daily/` с файлом. На следующий день — второй файл. Если в логах `ОШИБКА` — пришлите мне текст ошибки (без паролей).

## 4. Проверка восстановления («учения»), раз в квартал
Копия, которую ни разу не восстанавливали, не считается копией.
1. Скачайте любой файл `*.dump.enc` из корзины.
2. Создайте **новую** пустую базу (в Railway: New → Database → PostgreSQL, временную; не трогайте рабочую).
3. На компьютере с установленным клиентом PostgreSQL 18: `BACKUP_PASSPHRASE='…' ./backup/restore.sh gulf-….dump.enc "<адрес временной базы>"`.
4. Проверьте: `psql "<адрес>" -c "select count(*) from orders"` — число заказов близко к рабочему.
5. Удалите временную базу.
Если удобнее — попросите меня провести учения: пришлите файл копии, пароль задайте в Railway/на своём компьютере (не в чат).

## 5. Инструкция: авария, база потеряна или испорчена
1. **Остановить запись.** Railway → служба `gulf-bot` → Settings → остановить (Remove deployment / Stop). Клиенты увидят недоступность — это лучше, чем заказы в испорченную базу.
2. **Не удалять** старую службу `Postgres`/том до успешного восстановления (в нём могут быть данные, которые ещё можно спасти).
3. Создать **новую** службу PostgreSQL (New → Database → PostgreSQL). Взять её адрес.
4. Взять последнюю копию из корзины `daily/` (имя содержит дату и время UTC).
5. Восстановить: `BACKUP_PASSPHRASE='…' ./backup/restore.sh <файл> "<адрес новой базы>"` (клиент PostgreSQL 18).
6. Проверить: число заказов, последний заказ по дате (`select order_number, created_at from orders order by id desc limit 3`).
7. Railway → `gulf-bot` → Variables → `DATABASE_URL` заменить на адрес новой базы (внутренний, `*.railway.internal`).
8. Запустить `gulf-bot`. В логах должно быть `[OK] База данных инициализирована` и `БОТ ГОТОВ`.
9. Сделать тестовый заказ, убедиться, что админ-чат получил уведомление и вкладка «Журнал» → «Состояние системы» зелёная.
10. Записать в `docs/MEMORY.md`: дата аварии, какая копия использована, сколько заказов потеряно (заказы после времени копии клиентам придётся оформить повторно; их можно найти в уведомлениях админ-чата Telegram).
11. Через неделю удалить старую службу Postgres и пустые лишние службы.
